**Claim.** The [Veritas](../Veritas) credential verifier never accepts a credential that
is revoked or expired — and it stays correct under *every* ordering of issue, revoke,
clock-tick and verify events, not just the happy path. This is proved by exhaustive model
checking in **TLA+ / TLC**, not asserted.

## The property

> In no reachable state does a verifier accept a credential that is, at that moment,
> **revoked or expired**.

TLC explores the entire reachable state space of the model and checks this invariant at
every state. For the correct verifier it finds **no violation across 388 reachable states**
(depth 9) — a proof for the bounded model.

## The model (`VeritasRevocation.tla`)

A credential is *issued* with an expiry, may be *revoked*, and may be *verified* at any
time; the clock *ticks* forward. Signature validity is abstracted as membership in
`issued` (an unforgeable, recognised credential). The verifier accepts iff the credential
is recognised and passes each **enabled** guard:

```
Accepts(c) == c \in issued
           /\ (CheckExpiry      => time <= exp[c])   \* valid up to and including exp
           /\ (CheckRevocation  => c \notin revoked)
```

`CheckExpiry` and `CheckRevocation` are constants, so the *same* model proves the property
holds **and** that each guard is load-bearing.

## The results — proof, and the necessity of each guard

| Config | `CheckExpiry` | `CheckRevocation` | TLC result |
|---|---|---|---|
| `correct` | TRUE | TRUE | ✅ **No violation** — invariant holds over all 388 states |
| `no_revocation` | TRUE | FALSE | ❌ **Counterexample**: `Issue → Revoke → Verify` accepts a **revoked** credential |
| `no_expiry` | FALSE | TRUE | ❌ **Counterexample**: `Issue(exp=1) → Tick → Tick → Verify` accepts an **expired** credential |
| `correct_3x5` | TRUE | TRUE | ✅ **No violation** at a larger bound: 3 credentials, horizon 5 — **15,966 states** (depth 13) |

Turning a guard off doesn't just weaken the system in theory — TLC produces the **exact
shortest trace** that breaks it. That's the difference between "we check revocation" and
"removing the revocation check is provably unsafe, and here is how." Full transcripts are
in `results/`.

## Trace validation — the model against the real code

A proof about a model is only as good as the model's fidelity to the code. `trace/validate.php`
closes that gap: TLC dumps **every reachable state** of the correct model (`-dump`), and each one is
replayed against the **real Veritas PHP verifier** — a genuinely signed credential with the state's
expiry, the state's revocation list and the state's clock; "not issued" becomes a credential signed by
a key the verifier does not trust. Every model decision must match the code's decision.

**What it found.** The first run disagreed on 84 of 776 decisions, all at one instant: the second a
credential expires (`now == exp`). The code accepts it; the original model treated it as expired. The
Veritas format spec and all four reference verifiers define *expired iff `exp < now`*, so the
**model** was proving the property for a stricter boundary than the one shipped. The model now uses
the documented rule (`time <= exp`), and trace validation passes on every decision at both bounds:
**776 / 776** (388 states × 2 credentials) and **47,898 / 47,898** (15,966 states × 3 credentials). Transcripts:
`results/trace_correct.txt`, `results/trace_correct_3x5.txt`. (The first, failing run used a state set
generated by an independent re-implementation of the model with the same 388-state count; the
passing runs use TLC's own dump.)

## Offline verification — what a revocation cache does (`VeritasRevocationCache.tla`)

In production, verifiers work offline from a cached copy of the signed revocation list. The cache
model adds `Refresh` (fetch the current list) and a **freshness guard**: refuse to verify from a cache
older than `MaxStale`.

| Config | Freshness guard | Property | TLC result |
|---|---|---|---|
| `cache_bounded` | ON | `BoundedStaleness`: never accept a credential revoked more than `MaxStale` ago | ✅ **No violation** across **24,600 states** |
| `cache_unbounded` | OFF | `BoundedStaleness` | ❌ **Counterexample**: `Issue → Revoke → Tick → Tick → Verify` (accepted 2 ticks after revocation) |
| `cache_strict` | ON | `StrictRevocation`: never accept a revoked credential | ❌ **Counterexample**: `Issue → Revoke → Verify` — the window is inherent to offline checking |

The honest conclusion: an offline verifier **cannot** guarantee instant revocation; it can guarantee
that revocation takes effect within `MaxStale`, and only if it fails closed on a stale list.

## Run it

```bash
bash run-checks.sh      # downloads tla2tools.jar if needed; a JVM, plus php + ../veritas/src for trace validation
bash run-all-docker.sh  # everything in throwaway Docker containers (Windows Git Bash too)
```

The harness is self-asserting: it fails unless every outcome above is exactly as stated, and CI
runs the model checks **and** the trace validation (checking out the Veritas repo) on every push.

## Scope & honesty

- This is a **bounded** model (2 credentials × horizon 3, and 3 credentials × horizon 5). TLC proves the property
  over that finite space exhaustively; it is strong evidence, not a proof for unbounded
  parameters (that needs an inductive invariant / TLAPS, a natural next step).
- Cryptographic soundness is **abstracted**: `issued` stands in for "signature valid and
  recognised." The proof is about the **protocol logic** (expiry + revocation + ordering),
  which is where lifecycle bugs actually live; the signature layer is verified separately in
  Veritas by cross-implementation test vectors.

## Why this is a technical-depth proof

Formal verification is the strongest correctness signal in security engineering, and
almost no practitioner reaches for it. Modelling a real protocol, stating a safety
property, and having a model checker both confirm it and generate counterexamples for the
broken variants demonstrates a way of thinking about correctness — under adversarial
interleaving — that a 20-year researcher recognises immediately.
